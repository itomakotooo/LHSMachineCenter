## 4. Design: Play-Type Plugin Model (REVISED)

### 4.1-rev Plugin Contract — Call-Ordering Model and Read-Only Rule

The core concern from `05_critique.md TC-1 / SQ-1 / SQ-2` is that `04` asserted byte-identical output but provided no call-ordering model. This section specifies the ordering explicitly so the byte-identical gate is an achievable property, not a hope.

#### Per-round execution order (inside the per-robot inner loop)

For each round in a robot's round list, the parse loop executes in this strict sequence:

```
Step U1: Universal body reads raw round_dict fields.
         Computes: is_paid (from CostCredits or parse_state.cost_credits_unreliable),
                   win_credits (from WinCredits),
                   authoritative_pay_ids (from PayoutIdToWinAmount),
                   payline_records (from PayoutByPayline).
         Writes derived fields into the LOCAL round context (NOT into round_dict).
         Derived values are passed EXPLICITLY to accumulator on_round() as separate args.

Step U2: Session-level accumulators run (inline, universal):
         _close_session, _flush_bonus_chain, symbol/payline count loops.
         These read from the local round context, NOT from accumulator output.
         Invariant: session accumulators complete before any plugin accumulator fires.

Step P:  For each active plugin accumulator, in MECHANIC_DEPS topo-sort order:
         acc.on_round(round_dict, round_ctx)
         where round_ctx is a FROZEN named-tuple carrying the U1-derived values.
         round_dict is the RAW upstream dict. Accumulators may read round_dict freely.
         Accumulators MUST NOT write to round_dict (enforced by protocol doc; see below).
         Accumulators write ONLY to self.* (their own internal state).
```

This ordering means:

- `is_paid` is computed before any accumulator fires. The `CostCreditsReliabilityProbe` result (`parse_state.cost_credits_unreliable`) is available at Step U1 because it runs PRE-LOOP (see Section 4.5). There is no chicken-and-egg: the probe runs once per chunk before the robot loop begins.
- `_close_session` runs at Step U2, using the local round context, not accumulator output. Trigger-session detection (which was previously inline at this step) moves to the plugin's `on_round`. The session close logic therefore reads from the `round_ctx` already produced at U1, not from plugin-accumulated state. This is the direct answer to `05_critique.md SQ-1 / R1-1`: `_close_session` does NOT read BCM-derived state during the loop; it reads universal fields (is_paid, win_credits, pay_ids) from the frozen `round_ctx`.
- Plugin accumulators run AFTER session accumulators. They observe the fully-computed `round_ctx` for each round. Their writes go only into self.*.
- `MECHANIC_DEPS` topo-sort governs the order among plugin accumulators (same sort used for emit()). This directly addresses `05_critique.md EC-6`: yes, `MECHANIC_DEPS` ordering applies to both `on_round()` dispatch and `emit()` dispatch.

#### The read-only contract on round_dict

Accumulators must not mutate `round_dict`. This is a documented protocol requirement, not an enforced ABC method. Enforcement approach: the contract is stated in `MechanicAccumulator`'s class docstring and in the implementation guide. The `round_ctx` frozen named-tuple is the primary vehicle for computed fields. If an accumulator needs to communicate a derived field to a downstream accumulator that runs in the same round iteration (e.g., BCMBase writes `is_bcm_trigger=True`), it does so by writing to its own state and the downstream accumulator reads from the upstream accumulator's instance via the `peer_accumulators` argument to `on_round()`:

```
acc.on_round(round_dict, round_ctx, peer_accumulators: dict[str, MechanicAccumulator])
```

`peer_accumulators` is a dict from FEATURE_ID to the already-fired accumulator instances (those earlier in topo-sort). A downstream accumulator can read (NOT mutate) any peer's `.state` property. This is the designed channel; `round_dict` mutation is never needed.

#### Why byte-identical is achievable

With this ordering model, byte-identical follows from three properties:

1. **Float accumulation order is preserved.** The universal body accumulates `chunk_win`, `session_win_sum`, payid win sums in exactly the same order as before the carve (Step U1+U2 is identical in behavior to the current inline code; the B functions that move to plugins are read by `on_round`, not by the universal body during the loop). No float is summed in a different sequence.

2. **Dict key insertion order is preserved.** The chunk dict is assembled at `finalize()` by calling `to_chunk_partial()` for each accumulator and merging in MECHANIC_DEPS order. The resulting key sequence is deterministic and must match the key sequence of the current inline code. The implementer is responsible for matching key names and insertion order exactly during the carve. The byte-identical golden test is the automated guard.

3. **Stash-write timing is unchanged.** The universal body assembles the chunk dict and returns it. `main()` then stashes keys (e.g., `_collect_mechanic_data`) from the merged chunk dicts. The stash writes happen at the same stage (post-parse, pre-finalize) as today. Accumulators deliver their chunk partials at `finalize()`, which is called before `parse_chunk_response` returns. This is identical to the current call timing of `compute_trigger_sessions` and `detect_cycle_peak` (both currently called inside `parse_chunk_response` before it returns).

Ground truth anchor: `01_pipeline_map.md §2 Stage 1` confirms `parse_chunk_response` returns a dict. `main()` reads from that dict at `Stage 2`. `_compute_bonus_correction` runs at Stage 2 (after all chunks are parsed), reading `all_cycle_peaks` from the merged chunk dicts. `all_cycle_peaks` is written by `BCMBaseAccumulator.to_chunk_partial()` at `finalize()`, which runs inside `parse_chunk_response` before it returns. There is no timing gap.

#### Updated MechanicAccumulator ABC sketch

```
class RoundCtx(NamedTuple):
    """Frozen per-round context from the universal body (Step U1).
    Accumulators read from here instead of re-deriving universal fields.
    round_dict is still passed for plugin-specific raw fields."""
    is_paid: bool
    win_credits: int
    authoritative_pay_ids: frozenset[str]
    round_idx: int
    spin_type: int
    remarks: str


class MechanicAccumulator(ABC):
    """Per-robot stateful accumulator. Instantiated fresh per robot per chunk.

    CONTRACT:
    - on_round() MUST NOT mutate round_dict.
    - on_round() MAY read peer_accumulators[fid].state for peers earlier in topo-sort.
    - to_chunk_partial() is called ONCE per robot after on_robot_end(); result merged into chunk dict.
    - The merged chunk dict key names MUST exactly match those produced by the current inline code
      (verified by byte-identical golden tests).
    """

    @property
    @abstractmethod
    def state(self) -> dict:
        """Read-only snapshot of current accumulation state. Used by peer accumulators."""

    @abstractmethod
    def on_round(
        self,
        round_dict: dict,       # raw upstream round — READ ONLY
        ctx: RoundCtx,          # universal-derived context — READ ONLY
        peers: dict[str, "MechanicAccumulator"],  # earlier-in-topo-sort peers
    ) -> None:
        """Called for every round in this robot's round list, in topo-sort order."""

    @abstractmethod
    def on_robot_end(self, all_rounds: list[dict], all_ctxs: list[RoundCtx]) -> None:
        """Called once after all on_round() calls for this robot.
        Use for post-hoc corrections that require the full robot view.
        Note: accumulators that track incremental state via on_round() typically
        implement this as a no-op."""

    @abstractmethod
    def to_chunk_partial(self) -> dict:
        """Return this robot's mechanic contribution to the chunk dict.
        Called after on_robot_end(). Keys must match current inline code output."""
```

### 4.2 ClaimSignature — the auto-detection predicate

*(Unchanged from `04_architecture_proposal.md §4.2`, except the addition below.)*

**Evaluation scope clarification** (addresses `05_critique.md SQ-5`):

Each `ClaimSignature` field is evaluated against a specific round population:

- `required_fields`: evaluated against rounds where `CostCredits > 0` OR `parse_state.cost_credits_unreliable=True` (paid rounds). A field appearing only on bonus rounds is a bonus-round signal, not a paid-round field. Exception: if the field name starts with `"_bonus_"` (a convention for bonus-round-only fields), it is evaluated against `CostCredits=0` rounds.
- `required_bonus_remark_pattern`: evaluated against `CostCredits=0` rounds only (bonus rounds). Case-sensitive by default. Plugins that need case-insensitive matching set `bonus_remark_case_insensitive=True` on the signature (a new optional field). The evaluator uses `re.search()` (not `re.match()`), so the pattern must be anchored if exact-match is needed.
- `required_trigger_pay_id`: evaluated against paid rounds. The pay_id must appear in `PayoutIdToWinAmount` on at least one paid round in the sample.
- `exclude_if_fields_present`: evaluated against any round. If any round in the sample has the excluded field, the signature does not apply.

Minimum sample size for detection: the detector uses ALL rounds in `chunk_0001` up to 5,000 rounds maximum (not "first 500-2000"). This addresses `05_critique.md SQ-6 / EC-2` by giving rare triggers more chances to appear. Machines where a signature's required signal does not appear in 5,000 rounds are detected as NOT having that play-type, and the `unknown_bonus` fallback fires an ONBOARDING ALERT (addressed in Section 9-rev, Phase 3 handling). This is accepted: the 5,000-round sample is sufficient for triggers with rate > ~0.1% (5 expected events). Below that rate, the ONBOARDING ALERT is correct behaviour — a human must confirm.

### 4.5 (NEW) PreParseProbe — Lifecycle for Pre-Loop Universal Flags

**Motivation** (from `05_critique.md TC-2` and `06_validation.md Item A`): M10/M23/M131/M133 have `CostCredits=0` on every round despite real player wagers. The current `parser.py:L626-648` detects this by scanning the first 200 rounds BEFORE the per-robot loop begins, setting `cost_credits_unreliable=True`. The standard `MechanicAccumulator` lifecycle (on_round → finalize → result) cannot satisfy this pre-loop ordering requirement because `is_paid_round()` must read `cost_credits_unreliable` at Step U1 of every round.

**Taxonomy correction**: `02_taxonomy.md §A2` states "`CostCredits > 0` = paid (fleet-universal)." This is INCORRECT for the M10 family. The correct statement is: "`CostCredits > 0` = paid for machines where CostCredits is reliable. For machines where `parse_state.cost_credits_unreliable=True`, ALL rounds are treated as paid (CostCredits is always 0 but `BetAmount > 0`)." The `PreParseProbe` is the mechanism that sets this flag.

**Auto-detection of unreliable CostCredits** (the probe does NOT use a human-maintained machine list): the probe examines the first 200 rounds of the first robot in the chunk and sets `cost_credits_unreliable=True` when BOTH conditions hold: (a) every round in those 200 has `CostCredits=0`, AND (b) at least one round has `BetAmount > 0`. This is the exact logic currently at `parser.py:L626-648`. It self-detects from rawdata without any machine list. `parse_state.cost_credits_unreliable` defaults to `False` and is only flipped by this probe.

#### PreParseProbe ABC

```
class PreParseProbe(ABC):
    """A probe that runs ONCE per chunk BEFORE the per-robot loop begins.
    Its results are written to ParseState and read by the universal loop body.

    Lifecycle:
    1. probe.run(sample_rounds, parse_state) — runs once before the outer robot loop.
       sample_rounds: first min(200, len(chunk_robots[0].rounds)) rounds of the first robot.
       parse_state: a MUTABLE ParseState object shared with the universal loop body.
    2. The universal loop body reads parse_state attributes at Step U1 of every round.
    3. Probes do NOT implement on_round() — they are not accumulators.
    4. Multiple probes may run; they are applied in registration order (no dependency ordering needed —
       probes write to disjoint parse_state fields by design).

    A PlayTypePlugin that requires a PreParseProbe implements get_probe() in addition to
    make_accumulator(). If get_probe() returns None (default), no probe runs for that plugin.
    """

    @abstractmethod
    def run(self, sample_rounds: list[dict], parse_state: "ParseState") -> None:
        """Examine sample_rounds and set parse_state flags as needed.
        Must be idempotent (safe to call multiple times on the same parse_state)."""
```

#### ParseState fields written by probes

`parse_state.py` (already in `_CLOSURE_FILES`, already A-class) gains these fields:

```
cost_credits_unreliable: bool = False
    # Written by: CostCreditsReliabilityProbe
    # Read by:    universal U1 body — overrides is_paid to True when set
```

Additional probe-written flags can be added in future (each probe owns a disjoint field; no ordering dependency between probes).

#### Updated PlayTypePlugin sketch (adds get_probe())

```
class PlayTypePlugin(AnalyzerFeature):
    CLAIM_SIGNATURE: ClassVar[ClaimSignature]
    MECHANIC_DEPS: ClassVar[tuple[str, ...]] = ()

    def get_probe(self) -> PreParseProbe | None:
        """Return a PreParseProbe instance, or None if this plugin needs no pre-loop probe."""
        return None

    @abstractmethod
    def make_accumulator(self, machine_config: "MachinePlayTypeConfig") -> MechanicAccumulator:
        """Return a fresh accumulator for one robot."""

    # extract/reduce/emit inherited from AnalyzerFeature for the display-payload role.
```

#### CostCreditsReliabilityPlugin implementation sketch

```
# fresh_slotlab/analyzer/play_types/lockrepin_base.py

class CostCreditsReliabilityProbe(PreParseProbe):
    def run(self, sample_rounds, parse_state):
        if len(sample_rounds) < 5:
            return  # insufficient sample; default (False) stays
        all_zero = all(r.get("CostCredits", -1) == 0 for r in sample_rounds)
        any_bet = any(r.get("BetAmount", 0) > 0 for r in sample_rounds)
        if all_zero and any_bet:
            parse_state.cost_credits_unreliable = True


class LockRespinPlugin(PlayTypePlugin):
    CLAIM_SIGNATURE = ClaimSignature(
        required_fields=frozenset({"LockLines"}),
        required_bonus_remark_pattern=None,
    )
    # Note: CostCredits > 0 is NOT in required_fields for this plugin.
    # The signature matches on LockLines presence (present on all M10 rounds).

    def get_probe(self):
        return CostCreditsReliabilityProbe()

    def make_accumulator(self, machine_config):
        return LockRespinAccumulator(machine_config)
```

The probe runs before any `on_round()` call. By the time `LockRespinAccumulator.on_round()` fires, `parse_state.cost_credits_unreliable=True` is already set, and the universal U1 body has already applied the override to `is_paid`. The accumulator receives the correct `ctx.is_paid=True` for all M10 rounds without needing to re-examine CostCredits itself.

### 4.6 (NEW) General Claim Precedence / Tie-Break Rule

**Motivation** (from `05_critique.md TC-3`): The validator found dual-claim conflicts — M275 ST=126 (BCMFreespin + ScatterFreespin) and M120 ST=138 (MultiSymbolCollection + ScatterFreespin). The original proposal handled these per-case. The critic correctly warns this pattern recurs across ~310 remaining machines and needs a general rule.

**The general precedence rule:**

> **Structural-exclusion first, then specificity, then dep-subordination.**

Applied in this order:

**Rule 1: Structural exclusion wins.** If plugin A's `ClaimSignature.exclude_if_fields_present` is non-empty and the machine's rawdata sample contains any of those fields, plugin A does NOT claim the ST regardless of its other signals. This is a hard veto. Examples: `ScatterFreespinPlugin` has `exclude_if_fields_present=frozenset({"CollectCount","AccCredits"})` → it does not claim any bonus ST on BCM machines (where CollectCount is present on paid rounds). This resolves the M275 ST=126 conflict: ScatterFreespin vetoes itself on BCM machines; BCMFreespinPlugin claims ST=126 unopposed.

**Rule 2: Dep-subordination.** If plugin A declares `MECHANIC_DEPS=("scatter_freespin",)` and plugin B is `scatter_freespin`, then when both A and B claim the same ST, B gets primary ownership of that ST and A is a subordinate observer. The ST is assigned to B in `st_map`. A's accumulator still fires for that ST (to do its additional tracking), but it is listed as a dep-subordinate, not a co-owner. This resolves the M120 ST=138 conflict: `MultiSymbolCollectionPlugin` has `MECHANIC_DEPS=("scatter_freespin",)` → ST=138 is assigned to `scatter_freespin`; `MultiSymbolCollectionPlugin` observes those rounds as a subordinate.

**Rule 3: Most-specific signature wins.** If Rule 1 and Rule 2 do not resolve the conflict, the plugin with more `required_fields` in its `ClaimSignature` is more specific and wins. Rationale: a plugin whose signature requires `{"DollarCount","ChosenDollar","OfferValue"}` (3 fields) is more specific than one requiring only `{"DollarCount"}` (1 field). In case of a tie (same number of required fields), an ONBOARDING ALERT fires — this is the true ambiguity case requiring human review.

**Why this is not "hundreds of alerts in Phase 3"** (responding to `05_critique.md TC-3`): The two observed conflicts both resolve deterministically under Rules 1 and 2 respectively. The structural-exclusion rule (Rule 1) handles the class of BCM-vs-scatter conflicts systematically — adding `exclude_if_fields_present=frozenset({"CollectCount","AccCredits"})` to ScatterFreespinPlugin resolves ALL BCM+scatter machines at once, not per-machine. The dep-subordination rule (Rule 2) handles any plugin that is by design a "tracker on top of another mechanic." Alerts fire only for genuine novel ambiguity that requires a new plugin or a new exclusion rule — at which point a single code change (adding a field to an existing plugin's `exclude_if_fields_present` or adding a `MECHANIC_DEPS` declaration) resolves the whole class.

**Applying the rule to the two confirmed conflicts:**

M275 ST=126 (BCMFreespin vs ScatterFreespin): Rule 1 applies. `ScatterFreespinPlugin.exclude_if_fields_present=frozenset({"CollectCount","AccCredits"})`. M275 paid rounds have CollectCount. ScatterFreespin vetoes itself. BCMFreespinPlugin claims ST=126. The BCMFreespinAccumulator internally distinguishes scatter-triggered (pay_id=666) from BCM-peak-triggered (CollectCount=1000) freespin sessions by tracking the preceding paid round's trigger signal. No ONBOARDING ALERT; no fork rule needed in the auto-detector.

M120 ST=138 (MultiSymbolCollection vs ScatterFreespin): Rule 2 applies. `MultiSymbolCollectionPlugin.MECHANIC_DEPS=("scatter_freespin",)`. ST=138 is assigned to `scatter_freespin`. `MultiSymbolCollectionPlugin` fires as a subordinate observer on those rounds to track `RewardIdToCollectAmount`. No ONBOARDING ALERT.

### 4.7 (NEW) `display_features_for_play_types()` — Manifest-Replacement Contract

**Motivation** (from `05_critique.md SQ-9`): The hash composition in `04 §7.2 Step 3` calls `display_features_for_play_types(play_type_config.active_plugins)` but the function was unspecified. This section specifies it.

**Design decision**: the 9 existing display plugins are NOT all universal. The manifest system declared all 9 for nearly every machine, but that was lazy. The new system narrows by active play-types. The mapping is declared by each display plugin via a new class variable `REQUIRES_PLAY_TYPES`:

```
class AnalyzerFeature(ABC):
    # Existing fields...
    REQUIRES_PLAY_TYPES: ClassVar[frozenset[str] | None] = None
    # If None: feature applies to ALL machines (universal display feature).
    # If non-empty frozenset: feature applies only to machines with at least one
    # of the listed play-type FEATURE_IDs active.
```

The function implementation:

```
def display_features_for_play_types(
    active_plugin_fids: list[str],
    all_display_features: list[AnalyzerFeature],
) -> list[str]:
    """Return the FEATURE_IDs of display features that apply to a machine
    with the given active play-type plugins."""
    result = []
    for feat in all_display_features:
        if feat.REQUIRES_PLAY_TYPES is None:
            result.append(feat.FEATURE_ID)  # universal
        elif feat.REQUIRES_PLAY_TYPES & set(active_plugin_fids):
            result.append(feat.FEATURE_ID)  # at least one matching play-type
    return sorted(result)
```

**Mapping for the 9 existing display features:**

| Feature | `REQUIRES_PLAY_TYPES` | Rationale |
|---|---|---|
| `payouts_by_spin_type` | `None` (universal) | All machines have spin-type payouts |
| `reel_marginal_by_spin_type` | `None` (universal) | All machines have reel distributions |
| `bankruptcy_simulation` | `None` (universal) | Session simulation applies to all |
| `multiplier_profile` | `None` (universal) | Multiplier bucket is universal |
| `multiplier_wild` | `frozenset({"wild_nudge"})` | Only wild-nudge machines have wild multiplier surfaces |
| `machine_mechanics` | `None` (universal) | Detection results are reported for all |
| `upstream_feature_breakdown` | `None` (universal) | Upstream feature tally is universal |
| `collect_mechanic` | `frozenset({"bcm_base"})` | BCM collect cycle stats only relevant for BCM machines |
| `bonus_chain_dynamics` | `frozenset({"bcm_freespin","scatter_freespin","lockrepin_base","topdollar"})` | Only machines with bonus chains produce chain dynamics |

**Effect on pure-paid machines (M14)**: `active_plugins=["pure_paid"]`. `display_features_for_play_types` returns `payouts_by_spin_type, reel_marginal_by_spin_type, bankruptcy_simulation, multiplier_profile, machine_mechanics, upstream_feature_breakdown` — 6 features. `collect_mechanic` and `bonus_chain_dynamics` do NOT apply. `multiplier_wild` does not apply. This is a visible output change from today (today M14's manifest lists all 9). The difference: `collect_mechanic` section disappears from M14's report. This is correct, not a regression — M14 has no collect mechanic to display. The byte-identical gate for M14 is adjusted accordingly: the gate checks the 6 applicable features, not 9.

**Hash composition effect**: `display_features_for_play_types` is deterministic from `active_plugins`. No manifest file is needed. The sorted list of applicable display feature FEATURE_IDs is the input to Step 3 of the hash composition. This is fully specified.

## 7. Hash / Version Model

### 7.1-rev New `_CLOSURE_FILES` — Partial-File Carve Clarification

**The arithmetic question** (from `05_critique.md SQ-4`): files like `round_classification.py` contain both A-class functions (stay in base) and B-class functions (move to plugins). A file cannot simultaneously be in and out of `_CLOSURE_FILES`. The proposal must choose Option (a) or (b).

**Decision: Option (b) for all partial files.** The file STAYS in `_CLOSURE_FILES` but B functions are DELETED from it (moved to plugin files). The file shrinks; the A-class remainder stays in the closure.

Rationale for Option (b) over Option (a): Option (a) (relocate A functions to a new module) requires updating every import of `round_classification.is_paid_round` across all consumer scripts — `parser.py`, `scripts/infer_paytable.py`, `scripts/infer_bcm_pairing.py` (per `01_pipeline_map.md §5`). This is a significant refactor with silent-failure risk on scripts not in the pilot test suite. Option (b) (delete B functions, keep A functions in place) requires no import changes. The A-function remainder is small (~3 functions, ~80 lines for `round_classification.py`) and highly stable — it changes at the rate of universal semantics changes, which is infrequent. The hash benefit is: the B functions no longer live in the closure file, so editing them in plugins does not touch `round_classification.py` → no base_hash flip.

**Implications per file:**

## 9. Migration Plan (REVISED)

### Overall approach

Two changes to the original plan:
1. Trigger-session plugin is SPLIT into two plugins (decision justified in this section).
2. Config-retirement sequencing for rollback safety is made explicit.
3. `_collect_mechanic_data` stash is explicitly addressed in Phase 1.

### Decision: Trigger-Session Plugin Split (closes `05_critique.md R2-2` / Q1)

**Decision: Split into two plugins — `RemarkTriggerPlugin` (Type 1) and `WheelSelectorPlugin` (Type 2).**

Justification: `compute_trigger_sessions` (230 lines) covers two structurally different detection families. Type 1 (Remark-triggered: `is_new_trigger_remark` detects "Trigger" prefix in ReMarks) applies to machines like M31 (scatter freespin) and M15 (TopDollar). Type 2 (win==0 anchor: a paid round with WinCredits=0 + trigger pay_id starts a session) applies to machines like M273 (WheelSelector). If they are in one plugin, fixing a Type 2 bug for M273 re-flags M31 (which only uses Type 1) — strictly worse isolation than today's single `trigger_sessions.py`. The split gives: Type 1 edit re-flags ~13-15 Remark-trigger machines; Type 2 edit re-flags M273's 85 variants + other wheel machines. This isolation is the design goal.

The split is clean because the two families share no code beyond `_to_float_or_zero` (a 6-line arithmetic helper that can live in a shared `trigger_session_utils.py` module, a tiny A-class file). The double-count filter (`_round_has_credited_win`) is universal and stays in base (it already lives in `round_win.py:round_has_credited_win`).

**Plugin assignments:**
- `ScatterFreespinPlugin` (PT-2): uses `RemarkTriggerPlugin` logic internally (its `TriggerSessionAccumulator` is a `RemarkTriggerAccumulator` instance via composition, not subclassing). This avoids `ScatterFreespinPlugin` duplicating the Type 1 logic; it delegates to `RemarkTriggerPlugin`'s accumulator logic via `MECHANIC_DEPS`.
- `TopDollarPlugin` (PT-8): similarly delegates to `RemarkTriggerPlugin` accumulator logic.
- `WheelSelectorPlugin` (PT-15 non-BCM): owns the Type 2 logic independently.

## 13. (NEW) Edge-Case Handling Notes

One-line handling note per edge case listed in `05_critique.md §4`:

**EC-1 (Zero-round robot):** `on_round()` is called 0 times; `on_robot_end([], [])` is called with empty lists; `to_chunk_partial()` must return a dict of the same keys as non-empty robots but with zero/empty values. Each accumulator's `to_chunk_partial()` is responsible for this; the byte-identical test on the pilot machines catches any omission.

**EC-2 (First-chunk no bonus rounds):** Auto-detector with 5,000-round sample still finds no bonus ST. The machine is detected as pure_paid (if `CostCredits > 0` universally) or as `unknown_bonus` for the unclaimed bonus ST (ONBOARDING ALERT). The cached `MachinePlayTypeConfig` is written with this conservative assignment. On the next re-run (after the human resolves the alert), the config is updated. This is correct behaviour — it does not silently cache a wrong active_plugins list, because the `unknown_bonus` alert explicitly marks the config as incomplete.

**EC-3 (Variant with different SpinType than parent):** Per-variant auto-detection runs independently (per `06 §5 backward-compat table`). Each variant's `play_type_configs/<M$variant>/mode_<n>.json` is generated separately. Variant-specific ST remapping is handled naturally by the per-variant `st_map`. No special case needed.

**EC-4 (Accumulator exception mid-chunk):** The parse loop catches exceptions from `acc.on_round()`. On exception: log the error with round_idx and fid, mark the chunk as `partial_attribution=True` in the chunk dict, continue processing remaining rounds (the accumulator's state is invalid; its `to_chunk_partial()` returns an empty dict for that robot). The chunk is usable for universal metrics but its mechanic attribution is flagged. The report surfaces a warning. This is strictly better than the current behaviour (where an inline exception would abort the chunk).

**EC-5 (BCM cycle spanning robot boundary):** Addressed in OQ-2 above. Requires validator confirmation before Phase 1 implementation. Interim position: the current code's behaviour is preserved (if it currently handles cross-robot state, the accumulator handoff protocol will match it; if it currently does not handle it, the accumulator also does not handle it — byte-identical is maintained).

**EC-6 (`MECHANIC_DEPS` governs on_round() ordering):** Yes, explicitly confirmed in Section 4.1-rev: MECHANIC_DEPS topo-sort governs BOTH `on_round()` dispatch order (Step P) and `emit()` dispatch order. This is stated as a binding invariant in the `MechanicAccumulator` ABC docstring.
